## SSDの弱点: 書き込み増幅 (Write Amplification)

- SSDの内部はNANDフラッシュという仕組みで作られている（KIOXIA、昔の東芝メモリが作った）
- 特徴は、**一度書いた場所を直接上書きできない**こと

### 具体例: SSDの中で起きる増幅 (SSD WAF)

> Claudeが作ってくれた例

話を簡単にするため、SSDの1ブロックにページが4つだけ入るとする。最初、ブロックXに4つのデータA、B、C、Dが入っている状態。

```
ブロックX: [A] [B] [C] [D]   ← すべて有効
ブロックY: [ ] [ ] [ ] [ ]   ← 空き
```

ここでホスト（DBMS）がAとBを更新する。NANDは上書きできないので、新しいA'とB'は空きブロックYに書かれ、ブロックXの古いA、Bは「無効」になる。

```
ブロックX: [×]  [×]  [C] [D]   ← 半分が無効
ブロックY: [A'] [B'] [ ] [ ]
```

空きが少なくなってきたので、SSDはブロックXを消去して再利用したい。しかし、ブロックXにはまだ有効なCとDが残っている。消去は必ずブロック単位なので、先にCとDを別の場所にコピーしてからでないと消せない。

```
ブロックY: [A'] [B'] [C] [D]   ← CとDをコピー
ブロックX: [ ]  [ ]  [ ] [ ]   ← 消去して空きに
```

ホストが頼んだ書き込みはA'とB'の2ページだけだが、フラッシュに実際に書かれたのはA'、B'、C、Dの4ページ。つまり書き込み増幅率（WAF）は **4 ÷ 2 = 2** になる。CとDのコピーは、ホストからは見えない「余計な書き込み」である。

## データベース由来の書き込み増幅

SSDの書き込み増幅とは別に、データベース側の書き込み増幅もある。

- **Double Write Buffering (DWB)** というもの
  - MySQL, PostgreSQL, XtraDB, CedarDB が採用
  - ページをディスクに書き込む際に、別の領域に同じものを書いておく（バックアップ）
    - ページへの書き込みはアトミックにできない。DBのページ（4KiBや16KiB）はストレージが一度に書ける単位（512Bや4KiB）より大きいので、ページの書き込み中に落ちると新旧の内容が混ざったページ（torn page）が生まれてしまう
- これのせいで、DB由来の WAF が 2 になってしまう
